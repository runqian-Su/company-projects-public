# 脏数据处理策略

## 为什么这个项目重点是脏数据

考勤数据的难点通常不在算法，而在输入不稳定：

- 同一批输入里可能混有打卡明细、月度汇总、请假外出、排班排休、补卡记录等不同表；
- 同类表在不同月份、不同部门、不同系统导出时，文件名、sheet 名、表头行位置和列名都可能不同；
- 同一个人可能以姓名、工号、别名或带空格文本出现；
- 不同来源的列名和日期格式不一致；
- 打卡时间可能重复、缺失、非法；
- 请假、外出、排休等状态可能来自另一张表；
- 最终交付只允许白名单范围内的人员；
- 异常原因必须能追溯。

因此，本 Demo 把重点放在清洗链路和异常归因，而不是复杂界面。

## 处理顺序

```text
1. 文件索引：扫描输入目录，读取文件名、sheet 名、前几行预览和可用列。
2. 表类型识别：判断是打卡明细、请假外出、排班排休、补卡记录还是月度汇总。
3. 解析器路由：根据表类型进入对应 parser，不让一个通用读取器硬吃所有格式。
4. 表头定位：处理表头不在第一行、合并标题行、空列、重复列名等情况。
5. 字段归一：把不同来源列名映射成统一字段。
6. 身份解析：通过 employee_id、姓名和别名表确定标准员工。
7. 白名单过滤：只保留交付范围内人员，其他记录进入异常。
8. 时间清洗：解析、去重、排序打卡时间。
9. 来源合并：同人同日来自多个来源的打卡合并为一条日记录。
10. 状态覆盖：请假/外出/排休优先于普通打卡异常。
11. 规则判定：迟到、早退、缺卡、旷工等。
12. 汇总输出：生成标准记录、异常列表和人员汇总。
```

## 多格式表的处理

真实项目里，输入文件并不是一张稳定模板。管线需要先把“文件和表”处理干净，再处理“行和字段”。

处理方式是：

- 先建立一次运行内的工作簿索引，记录每个文件、sheet、前几行预览和可识别列；
- 通过文件名关键词、sheet 名、表头关键词和列组合判断表类型；
- 为不同表类型使用不同解析器，例如打卡明细、原始日志、请假外出、排班排休、补卡记录；
- 对表头行位置不固定的表，先探测表头，再读取明细区域；
- 对同义列名做字段映射，例如“姓名/员工姓名/人员姓名”、“日期/考勤日期”、“时间/打卡时间”；
- 对无法识别的文件或 sheet 不直接中断全链路，而是写入异常报告，供人工复核。

这一层的目标是把大量不同名称、不同格式、不同来源的表，先收敛成少数几类标准输入，再进入身份解析和规则计算。

## 异常不是失败

脏数据管线里，异常记录不是程序失败，而是交付物的一部分。

本 Demo 会把以下情况写入 `issues`：

- 找不到员工身份；
- 非白名单人员；
- 日期无法解析；
- 时间无法解析；
- 重复打卡；
- 缺少上班或下班打卡；
- 特殊状态覆盖普通异常。

这样业务人员可以复核“为什么这条记录这样算”，而不是只拿到一个黑盒结果。
