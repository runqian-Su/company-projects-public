# Ba 任务抽象说明

## 结论

在 BPO 多层数据平台中，Ba 任务是面向业务交付的最高操作抽象，封装一次从事实复制、任务级修正、构建、审计到发布消费的受控版本。

B 层回答的是：

```text
在某个项目、某个日期范围内，系统已经沉淀了哪些刚性事实？
```

Ba 任务回答的是：

```text
这一次业务分析、修正、构建、发布和交付，应该以哪个受控版本为准？
```

二者不是同一类对象。B 层是事实底座，Ba 任务是业务交付单元。

## 为什么不是直接消费 B 层

B 层的价值是稳定、可追溯、少歧义。它应尽量接近 A 层处理后的事实结果，不承载业务人员的临时判断、任务级预算、修正说明、二级汇总口径或发布状态。

但真实业务交付通常还需要：

- 按项目和日期范围创建一个明确任务；
- 将 B 层事实复制成任务内快照；
- 导入任务级输入，例如预算、确认表或补充口径；
- 对局部字段做可控修正；
- 先 diff 预览，再带原因 apply；
- 根据当前事实和输入重新构建二级结果；
- 通过 build 检查后发布；
- 让可视化、导出或交付包读取这个已发布版本。

这些动作如果直接发生在 B 层，会破坏事实层刚性；如果散落在 CLI、前端或脚本里，又会失去统一审计边界。所以 Ba 任务承担最高层业务操作对象的角色。

## 一个 Ba 任务包含什么

一个 Ba 任务不是单张编辑表，而是一组围绕 `ba_task_id` 聚合的状态和证据：

| 内容 | 说明 |
| --- | --- |
| 任务范围 | project、date_start、date_end、dataset |
| B 层快照 | 创建任务时从 B 层复制的事实副本和来源摘要 |
| 任务级输入 | 预算、确认值、补充参数等只在该任务内生效的输入 |
| 受控编辑 | 允许字段、diff 预览、apply 原因和应用结果 |
| 审计日志 | 谁在什么时间因为什么修改了哪些字段 |
| 构建状态 | 当前 build 是否成功，是否与最新事实修订一致 |
| 发布状态 | 哪个 build 被发布，何时发布，供下游读取 |
| 下游边界 | C 层 API、Agent Skill、可视化同步和导出读取的对象 |

## 分层关系

```text
A 层
  负责把原始输入清洗成事实。

B 层
  负责保存刚性事实，不作为人工修正和交付发布的对象。

Ba 层
  以 ba_task_id 封装一次完整业务操作：复制、输入、编辑、构建、发布。

C 层 / Skill / Visualization
  围绕 Ba 任务提供访问、操作和消费能力，最终消费已发布 Ba 任务。
```

## 设计边界

- Ba 可以从 B 复制事实，但不能反写 B。
- Ba 编辑必须经过 diff -> apply。
- apply 必须绑定有效 `diff_id` 和修改原因。
- publish 必须要求当前 build 成功。
- 高级看板和交付包应读取已发布 Ba 任务，不直接读取 B 层作为最终交付口径。
- 未发布 Ba 任务仍处于操作态，只能用于检查和编辑，不能作为可信交付版本。

## 作品集表达

这个抽象体现的不是“做了一个可编辑 SQLite”，而是把企业数据交付中的事实、修正、审计、构建、发布和消费边界收敛到同一个任务对象上。

对外展示时，可以概括为：

```text
B 层保证事实刚性，Ba 任务面向业务交付封装一次受控交付版本。
```
