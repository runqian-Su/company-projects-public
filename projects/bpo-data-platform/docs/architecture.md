# 架构说明

## 设计意图

这个 Demo 把 BPO 数据处理看作一套企业现代业务系统，而不是一组一次性脚本。

核心问题是：

```text
不同项目的原始格式和业务规则各不相同，
但组织仍然需要一套稳定方式来处理、存储、查看、干预、发布和可视化数据。
```

对应的架构答案是：

```text
A -> B -> Ba -> C -> Output / Visualization
```

## 系统总览

```text
原始输入
  - 图片
  - Excel 工作簿
  - 考勤记录
  - 业务记录
  - 预算或计划输入

        |
        v

A 层：事实处理层
  - 项目适配器
  - 解析器
  - OCR / Excel 标准化
  - 校验
  - 事实对象生成

        |
        v

B 层：刚性事实库
  - 中心 SQLite
  - 项目注册
  - 任务元数据
  - 源文件 hash
  - 稳定事实表
  - 入库与导出日志

        |
        v

Ba 层：任务级可控操作层
  - 每个任务一个 SQLite 切片
  - 从 B 层复制事实
  - 受控编辑
  - 业务输入
  - 二级表构建
  - 审计日志
  - 发布状态

        |
        v

C 层：本地数据管理平台
  - FastAPI API
  - React/Vite 前端
  - 查询与导出
  - 任务视图
  - 发布包 API

        |
        v

消费入口
  - CLI
  - Agent Skill
  - Excel 导出
  - 本地可视化池
```

## A 层

A 层是项目级原始数据处理层。

职责：

- 读取原始文件；
- 解析图片和 Excel；
- 处理格式不稳定、字段不一致、表头混乱等脏数据问题；
- 生成标准事实对象；
- 将验收通过的事实写入 B 层；
- 记录处理日志和源文件元信息。

A 层可以因项目而异，因为真实业务数据往往高度异构。系统其他层依赖的是 A 层输出的稳定事实对象，而不是原始文件本身。

本 Demo 中的 A 层是一个合成处理器：

```text
raw_day_records.csv + raw_person_day_records.json
  -> 字段清洗
  -> 类型转换
  -> 基础校验
  -> 源文件 hash
  -> B 层事实表
```

它不模拟 OCR、Excel 解密或真实客户项目适配，只展示“原始输入如何变成可治理事实”的最小链路。

## B 层

B 层是刚性事实层。

职责：

- 注册项目；
- 记录处理任务；
- 追踪源文件和 hash；
- 保存稳定事实记录；
- 支持只读查询；
- 支持受控导出；
- 作为下游 Ba 任务切片的数据来源。

规则：

- B 层的常规写入只能来自 A 层事实处理；
- B 层不是人工编辑界面；
- Ba 可以从 B 层复制，但不能反写 B 层；
- CLI 和 Skill 默认只能只读访问 B 层。

## Ba 层

Ba 层是任务级可控操作层。其中 Ba 任务是面向业务交付的最高操作抽象，封装一次从事实复制、任务级修正、构建、审计到发布消费的受控版本。它不是一张可编辑表的编号，而是一次分析、修正、构建、发布和交付的统一任务对象。

它存在的原因是：企业业务中经常需要在事实处理之后做受控干预，例如：

- 导入或确认预算；
- 调整任务范围内的记录；
- 构建二级分析表；
- 重建汇总视图；
- 发布一个供可视化和交付使用的版本。

Ba 不是 B 的替代品，也不是 B 的人工编辑入口。B 层回答“事实是什么”，Ba 任务回答“这次业务交付应以哪个受控版本为准”。

一个 Ba 任务聚合：

- 从 B 层复制的事实快照；
- 项目、日期和数据集范围；
- 任务级输入和受控编辑；
- diff/apply 审计记录；
- build 状态；
- publish 状态；
- C 层、Agent Skill 和可视化消费边界。

规则：

- 一个 Ba 任务切片只服务一个项目和一个声明范围；
- Ba 在任务创建时从 B 层复制事实；
- 编辑、输入、重算和发布日志都留在 Ba 内部；
- Ba 永远不反写 B；
- 已发布的 Ba 结果作为高级看板和交付包的可信来源。

## 层间衔接编排层

层间衔接编排层负责层与层之间的动作，不负责业务含义本身。

典型单元：

```text
a_to_b_fact_pipeline
b_to_ba_copy
ba_input_import
ba_build_trigger
ba_to_c_publish
c_to_output_export
```

职责：

- 运行层间衔接单元；
- 快照输入和输出；
- 记录日志和任务摘要；
- 校验必要 scope；
- 触发构建或导出命令。

不负责：

- 不定义项目 schema；
- 不保存业务主数据；
- 不绕过 Ba 的治理边界。

## C 层

C 层是本地应用入口。

职责：

- 提供 Web UI 和 API；
- 展示项目与任务状态；
- 查询 B 层事实或已发布 Ba 数据；
- 触发允许的编排动作；
- 生成导出和发布包；
- 为 CLI 和 Agent Skill 提供稳定集成点。

C 层不应独立拥有核心业务模型。它是建立在 B、Ba 和编排服务之上的应用层与访问层。

本 Demo 的 V3 不启动 Web 服务，只提供 C 层 API 契约：

```text
src/c_platform/api_contract.md
```

契约明确区分：

- 只读接口：项目、日期范围、B 层事实、Ba 任务记录、发布结果；
- 受控写接口：A->B 处理触发、Ba 任务创建、diff/apply、build、publish；
- 禁止能力：任意 SQL、任意 shell、直接写 B、跳过 diff、未 build 发布。

## CLI 与 Agent Skill 边界

CLI 和 Agent Skill 是受控入口。

第一阶段允许：

- 只读查询项目和数据集；
- 按日期范围查询；
- 受控 Excel 导出；
- 查看任务状态。

第一阶段禁止：

- 直接写 SQLite；
- 执行任意 shell；
- 触发 OCR 或原始数据处理；
- 编辑 B 层事实；
- 删除文件；
- 发送外部消息；
- 修改运行配置。

推荐链路：

```text
自然语言
  -> 意图解析
  -> 项目 / 数据集 / 日期范围校验
  -> 白名单 API 或 CLI
  -> JSON 结果或受控导出路径
```

## 可视化架构

可视化层采用“中心服务器 + 本地可视化池”模式：

```text
中心处理服务器
  - 持有主 SQLite 和处理 API
  - 负责数据生产和发布

客户端可视化应用
  - 通过 API 同步数据
  - 写入本机 SQLite 可视化池
  - 在本地完成筛选、聚合和图表渲染
```

这个模式适合小规模内部部署：

- 数据写入集中；
- 查看方以只读为主；
- 访问频率较低；
- 希望部署轻量；
- 第一阶段没有必要引入重型数据库和复杂运维体系。

本 Demo 中，可视化层只同步当前已发布 Ba 任务：

```text
GET /api/releases/{project_id}/current
  -> ba_task_id
  -> GET /api/ba/tasks/{ba_task_id}/records?dataset=day
  -> GET /api/ba/tasks/{ba_task_id}/records?dataset=person
  -> visualization/sync_release.py 写入本地 SQLite 可视化池
```

它不直接读取 B 层，因为 B 层是刚性事实底座，不包含 Ba 的任务级干预、构建和发布口径。未发布的 Ba 任务也不能作为看板数据源。
