# 建模决策说明

## 为什么先做对象库

财务应收分析的难点不只是把 Excel 转成数据库，而是要明确每一行明细归属于哪个业务对象。

本项目先建立多层对象：

```text
集团 -> 主体 -> 往来对象 -> 单据号 -> 应收事实
```

这样查询、汇总、明细追踪和一致性验证都可以围绕对象展开，而不是反复在原始行表里拼条件。

## 为什么事实挂在 L4 单据号对象上

应收余额通常不是孤立行指标。一个单据号下面可能有多条明细，部分行有余额，部分行已经核销或余额为零。

因此本 Demo 使用对象级命中规则：

```text
只要 L4 单据号对象下存在余额行，该单据号对象命中；
命中后保留该对象下全部明细，便于追踪上下文。
```

这比只过滤 `balance_amount > 0` 的行级做法更适合财务核对和业务解释。

## 为什么对象和事实分开

对象层回答“分析对象是谁”，事实层回答“对象在某个时点有什么指标”。

拆开后可以保留几个好处：

- 对象结构稳定，不随某次分析口径频繁变化；
- 同一对象后续可以挂载账龄、余额、核销状态、异常标签等不同事实；
- 汇总一致性可以沿对象层级逐层验证。

## 为什么强调一致性验证

财务数据模型不能只看查询结果是否能跑通，还要证明不同层级口径一致。

本 Demo 要求：

```text
集团余额
  = 主体余额汇总
  = 往来对象余额汇总
  = 单据号余额汇总
```

如果任一层不一致，说明对象生成、事实挂载或汇总查询存在问题。

## 项目节奏

真实项目中，核心对象模型和第一条可运行链路约半天完成。关键原因不是跳过建模，而是先把稳定对象抽象出来，再让 AI 协作快速补齐 schema、导入、查询和校验代码。

后续工作主要集中在口径验证、异常视图、导出交付、CLI、Skill 和本地平台入口，让模型从“能跑”变成“可复核、可交付、可复用”。
